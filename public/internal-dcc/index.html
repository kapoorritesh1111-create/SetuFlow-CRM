-- Migration 057 (FINAL — applied Apr 29 2026)
-- Drops category_type CHECK constraint. Makes column nullable.
-- Correct table names: product_pricing_rules + quote_version_line_items

BEGIN;

ALTER TABLE public.product_pricing_rules
  DROP CONSTRAINT IF EXISTS product_pricing_rules_category_type_check;

ALTER TABLE public.quote_version_line_items
  DROP CONSTRAINT IF EXISTS quote_version_line_items_category_type_check;

-- Safety net for auto-generated constraint name variants
DO $$
DECLARE r RECORD;
BEGIN
  FOR r IN SELECT conname, conrelid::regclass AS tbl FROM pg_constraint
    WHERE contype = 'c'
      AND conrelid IN ('public.product_pricing_rules'::regclass,
                       'public.quote_version_line_items'::regclass)
      AND pg_get_constraintdef(oid) LIKE '%category_type%'
  LOOP
    EXECUTE format('ALTER TABLE %s DROP CONSTRAINT IF EXISTS %I', r.tbl, r.conname);
  END LOOP;
END; $$;

ALTER TABLE public.product_pricing_rules ALTER COLUMN category_type DROP NOT NULL;
ALTER TABLE public.quote_version_line_items ALTER COLUMN category_type DROP NOT NULL;

UPDATE public.product_pricing_rules ppr
SET category_type = pc.name
FROM public.products p JOIN public.product_categories pc ON pc.id = p.category_id
WHERE ppr.product_id = p.id AND ppr.category_type IN ('chips', 'powders');

UPDATE public.quote_version_line_items qvli
SET category_type = pc.name
FROM public.products p JOIN public.product_categories pc ON pc.id = p.category_id
WHERE qvli.product_id = p.id AND qvli.category_type IN ('chips', 'powders');

COMMIT;

🔍 Where the code review differs from the surface review

Fast-field mode EXISTS — it was not missing. The GPT review said capture is still "15+ fields". Wrong. lead-drawer.tsx:1356–1410 has a dedicated 3-field trade show fast-field section (company, contact, product interest) with "Add more details" toggle. The problem is the activation condition is buggy: it requires lead.trade_event_id to be set on the lead object, but new leads don't have this set yet at render time. Fix: derive fast-field mode from initialEventId prop alone, not from lead.trade_event_id.
OCR card scan already uses AI vision. contact-ocr-provider.ts calls OpenAI vision API with business card classification, extracts structured fields, and prefills the form. The issue is discoverability, not capability — users must navigate to /contact-exchange/scan manually. The camera should auto-open from the trade show capture flow.
WhatsApp is the right decision — but it's stuck at schema. The communications table models WhatsApp as a first-class channel (channel: 'whatsapp'). The lead actions have quote_share_whatsapp_v1 templates. But there is no actual WhatsApp Business API call anywhere in the codebase. This is a 1-sprint integration, not a missing feature concept.
The ROI panel with event comparison is already built. trade-events/page.tsx computes lead count, quoted count, pipeline value, orders placed, and a vs-prior-event delta. This is more sophisticated than the GPT review acknowledged. It already answers "was Gulfood worth it vs SIAL last year".

⚠ Gaps the surface review missed entirely

No PWA manifest — confirmed in code. /public/ contains apple-touch-icon.png and icon.png but no manifest.webmanifest. Users cannot "Add to Home Screen". This is a 30-minute fix that would transform mobile adoption immediately.
Product category constraint is a hard ceiling. The quote_version_line_items table and product_pricing_rules table have CHECK (category_type = ANY (ARRAY['chips'::text, 'powders'::text])). Blue Orbit International sells: vacuum-cooked snacks, dehydrated powders, jaggery/sweeteners, onion/garlic products. Only chips and powders are valid. Every other product category the company sells cannot be priced correctly through the engine.
Client-side filtering ceiling. Lead filtering is done via useMemo in leads-workspace.tsx on the client. This works now but will degrade visibly at 200+ leads. No debounce on search, no server-side filtering, no pagination. This is the technical debt that will surface at first serious user.
No push notifications. The system has follow-up reminders stored in the database (next_follow_up_at), but no mechanism to notify users when a reminder fires. Users must open the app to see overdue leads. This makes the product reactive instead of proactive at exactly the moment it should be pushing.
