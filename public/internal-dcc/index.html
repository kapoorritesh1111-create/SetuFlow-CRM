Build, TypeScript, and DCC operating rules

Important: GPT sandbox should not attempt npm ci for this repo. The sandbox has repeatedly failed dependency restoration. Use static/code review here, then rely on user-provided or Vercel build logs for install/test/build proof.
Required proof loop after every pass No exceptions
StepRule
1. Read DCC firstOpen public/internal-dcc/index.html before changes and keep it as source of truth.
2. Fix smallest surfacePrefer existing components, handlers, route patterns, and types. No broad redesign during P0 hardening.
3. TypeScript safetyInspect interfaces before editing; do not add props not declared; guard nullable params; use existing unions/constants; preserve server/client boundaries.
4. Navigation actionsAny visible CTA must either navigate, open a modal/drawer, show validation, or be disabled with a tooltip. No silent no-ops.
5. Server actionsNo raw DB errors in UI. Qualify ambiguous SQL columns and return safe, typed error states.
6. Protected dataDo not mutate Q-00025 or d129ffe2-c913-4cf7-9a7b-86ea6c9da54e. Do not clean live users/invites/products without authorization.
7. Docs/DCC updateUpdate DCC, README, RELEASE_READINESS, and CHANGES every pass. Avoid new docs unless explicitly needed.
8. VerificationUser/Vercel runs npm ci, npm run test:all, and npm run build; paste logs for closeout.
Known TypeScript error prevention checklist Use before packaging
  • Never import server-only functions into client components; pass through actions/API boundaries.
  • When adding row clicks, keep nested button/checkbox handlers with event.stopPropagation().
  • When using router/search params, guard missing IDs and avoid assuming non-null string values.
  • When wiring tabs, use existing literal view names or extend the union type in one place only.
  • When adding route/drawer state, keep component state serializable and avoid passing functions across server/client component boundaries.
  • When changing SQL/query helpers, preserve return types and map optional DB fields defensively.
  • Prefer small patches and grep-based static checks over broad architecture movement.
